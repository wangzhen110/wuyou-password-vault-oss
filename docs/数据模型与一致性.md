# 数据模型与一致性

> 本文档记录**数据层的事实与约束**（id 规则、去重规则、冲突处理、编号分配、加密与记录的对应关系），来源为源码核对（2026-10-24）。
> 用途：**将来重构（如 4.3.0 云优先改造、更换存储引擎）时作为不能破坏的契约参考**。
> 每条结论都标注源码位置，方便复核；若代码变更，请同步更新本文档。

## 2. 记录 id 规则（核心契约）

```
createId():  crypto.randomBytes(16) → 32 位小写十六进制
             storage.js createId()
```

- **端侧生成**：新增记录时由端侧 `createId()` 生成（128 位随机，碰撞概率可忽略）
- **云端主键**：该业务 id **直接作为云数据库 `_id`**（`upsertOwnedRecord` → `findRecordById(collection, id)` 即 `where({ _id: id })`）
- **id 与内容完全无关**：id 不参与内容计算，**不看平台/账号/密码**，因此**内容相同的两条记录必然是两个不同 id**
- **不可变性**：id 一旦生成，全生命周期不变（更新只改内容字段，不改 id）

> **重构红线**：更换存储引擎时，必须保留「业务 id 即存储主键」这一语义，否则同步、取件、导入全链路失效。

## 3. 去重与冲突处理

**系统只按 id 去重，从不按内容去重。这是刻意设计，不要"优化"成内容去重。**

| 场景 | 规则 | 源码 |
|------|------|------|
| 端侧写入 | 按 id 查找并覆盖：`previousRecords.findIndex(record => record.id === entry.id)` | `storage.js:1099` |
| 旧数据迁移 | 按 id 匹配：`latest.findIndex(item => item.id === legacyEntry.id)` | `storage.js:602` |
| 待同步队列 | 按 id 入队/覆盖，同 id 后写覆盖先写 | `storage.js` `enqueue` 相关 |
| 导入备份（JSON） | 按 id 判断已存在则计入 `skipped`，**不比对内容** | `miniprogram/utils/import.js` |
| 云端写入 | `owner_mismatch`（同 id 属主不同）→ 拒绝；`record_id_conflict`（同 id 内容或来源冲突）→ 拒绝 | `sync/index.js` `upsertOwnedRecord` |

### 为什么不做内容去重（已确认的产品决策）

- 用户**确实可能需要两条内容相同的记录**（同一网站两个不同用途账号、同一密码用于不同平台）
- 内容去重会**静默合并**，造成数据丢失，且用户无法察觉
- 若未来要提示重复，正确做法是**添加时的轻量提醒（不拦截、不自动处理）**，绝不自动合并

## 4. 编号（seq）规则

- **分配者**：服务端 `allocateEntrySeq()`（`counters` 集合原子自增）
- **作用域**：**每用户独立**，从 1 开始连续递增
- **与 id 解耦**：seq 仅用于列表排序与用户可见的引用编号，**不参与加密、不进入导出文件**
- **冲突语义**：同一 id 重新上传时，若云端已有 seq 则沿用（`prior.seq`），不会重复分配

> **重构注意**：seq 是**展示层编号**，不可用作主键或幂等键；幂等键始终是 id（或 sync 的 `queue_id`）。

## 5. 加密与记录的对应关系

| 层级 | 加密参数 | 说明 |
|------|---------|------|
| **vault（每用户）** | `salt`（16 字节随机）+ `iterations`（60 万）+ `verifier` | 派生出一套 `encryptionKey` / `macKey`；`vault_meta` 本地与云端各存一份 |
| **记录（每条）** | 独立 `iv` + 独立 `mac`，共用 vault 密钥 | 同 id 不同用户 → 密钥不同 → 密文完全不同 |
| **备份文件（每次导出）** | **独立 salt**（`createVaultMeta` 每次新生成） | 同一用户两次导出的密文也不同 |

- **加密在端侧完成**，云端只存密文（`ciphertext` / `iv` / `mac` / `salt` / `crypto_version`）
- **verifier 构造**：`material = PBKDF2(password, salt, iter, 64B)` → `macKey = material[32..64)` → `verifier = HMAC-SHA256(key=macKey, msg='vault-verifier:v1')`（`crypto.js createVaultMeta`；`backupDownload` 云函数需复刻同一算法）

> **重构红线**：verifier 构造、salt 生成时机、密钥切分位置（0..32 / 32..64）**不可变更**，否则存量数据与备份全部无法解密。

## 6. 多设备同步的一致性模型

| 维度 | 现在的实现 |
|------|-----------|
| 冲突判定 | **以 id 为准**；同 id 内容不同 = 同一记录的不同版本，由 `updated_at` 与队列顺序决定先后 |
| 同步单位 | 单条记录（信封：id + seq + ciphertext + iv + mac + created_at + updated_at） |
| 待办队列 | 端侧 pending 队列按 id 记录未上传变更，上传成功按 `queue_id` 回执删除 |
| 触发时机 | 登录强制同步 / 前台每小时 / 回前台满 1 小时 / 手动 / 写入 debounce（见产品功能规格 7.4） |
| 隔离 | 全链路 `_openid` 过滤；跨用户不可见 |

## 7. 重构时必须保持的不变量（Checklist）

1. **业务 id = 存储主键**，且 id 由端侧随机生成（128 位）
2. **只按 id 去重**，禁止引入内容级自动合并
3. **seq 与 id 解耦**，seq 仅作展示编号
4. **verifier 算法、salt 时机、密钥切分**不得改动（存量数据兼容）
5. **加密在端侧完成**，云端不得出现明文或可解密材料（主密码/密钥永不上云）
6. **每用户 vault_meta 唯一**（`_id = openid`），轮换主密码走 CAS（`old_vault_meta` 匹配才换新）
7. **同步信封字段齐全**：id / seq / ciphertext / iv / mac / salt / crypto_version / created_at / updated_at
8. **取件链路**：`backup_links.link_id` 唯一，密码校验用 verifier，下载直链短时效 + 限次
