密码本开放 API · 原理讲解

为什么 API 只能「搬密文」、由第三方本地解密；授权令牌为什么泄露也不至于泄露密码。

一句话结论

你的密码本本质是端到端加密：主密码派生出的密钥只存在用户设备上，云端只有密文。 所以开放 API 只能传密文 + 公开参数，解密必须发生在第三方程序本地。 任何"服务端解密后返回明文"的 API 都会把产品从「密码管理器」降级为「密码托管」——一次被攻破就全库泄露。

一、你现在的密码本是怎么加密的

这是理解 API 方案的地基。全流程以一个主密码为源头，云端不参与任何解密。

1
主密码 → 派生密钥（PBKDF2-HMAC-SHA256，60 万次迭代） 主密码 + 16 字节随机盐 salt，迭代 60 万次，派生 64 字节材料，切成两把钥匙：AES 加密密钥 和 HMAC 认证密钥。60 万次的作用是让暴力猜密码的成本高到不可行。
2
每条记录独立加密（AES-256-CBC + Encrypt-then-MAC） 先用 AES 加密正文，再用 HMAC-SHA256 对「封套元数据 + 密文」做认证签名（mac）。解密时先验签名再解密，密文被篡改一个字节都会被拒绝。
3
云端只存两类东西：密文封套 + 公开参数 每条记录：nonce（随机数）、ciphertext（密文）、mac（认证券）。 另有一份 vault_meta：kdf、iterations、salt、verifier——全是公开参数，不含主密码、不含密钥。
4
verifier 只是"验密码"，不是"藏密码" 解锁时用派生密钥对固定内容做一次 MAC，与云端存的 verifier 比对：一致=主密码正确。它不能反推出主密码（是单向运算）。
关键性质

把云端数据库整个拷走，攻击者得到的是 salt + verifier + 一堆密文。 没有主密码，他既解不开密文，也只会被 60 万次迭代的 KDF 拖死在暴力破解上。这就是"零知识"的含义。

二、为什么不能做「云端解密」的 API

最省事的实现显然是：第三方带着账号调用 API，云端查库、解密、把明文密码返回。但这样一来：

做法上线后发生什么
云端解密服务端持有可解密密钥 ① 云函数或数据库一旦被攻破（或内部人员、日志误打印），全部用户的全部密码明文暴露； ② 用户对"密码管理器"的信任基础消失，属于产品定位级错误； ③ 合规上无法向用户承诺"我们看不到你的密码"。
本地解密云端只搬密文 即使令牌和密文全部泄露，攻击者拿到的仍是密文，还需要用户的密码主密码才能解开。安全等级与现在的小程序完全一致。

这也是行业通行做法：Bitwarden、1Password、KeePass 的同步/开放接口，全部是「服务端零知识 + 客户端解密」。

三、那 API 到底怎么让开发者"拿到密码"

分两段：先证明"你有权访问这个人的库"（授权），再在本地把密文解开（解密）。

3.1 授权：一次性码 → 令牌

1
用户在小程序里点「生成授权码」 云端生成 6 位一次性码，5 分钟有效。此时还没有任何权限。
2
第三方程序用它换令牌 POST /v1/token { code, device_name } → 云端返回 token（30 天有效）。令牌在云端只存 sha256 哈希，即使库被拖走也拿不到可用令牌。
3
用户在小程序里看到设备名并点「允许」 这一步防钓鱼：别人猜不到码也没用，必须本人在小程序里确认。授权列表可随时一键吊销。
为什么令牌泄露不等于密码泄露

令牌只授予"读取密文"的权限。拿到令牌的人能拉走 salt 与密文，但解不开——他缺的是只存在用户脑子里的主密码。 这和小程序"手机丢了也解不开"是同一个安全边界。

3.2 解密：SDK 在调用方本地完成

第三方程序拿到密文后，用 SDK 复现第 1、2 步的逆向过程：

// 第三方程序里（Node / 浏览器插件 / 自建服务）
const vault = new VaultClient({ token, masterPassword: '用户输入的主密码' });

await vault.unlock();
// 内部：GET /v1/vault/meta → 取 salt/iterations
//       PBKDF2(主密码, salt, 60万次) → AES密钥 + HMAC密钥
//       算 verifier 与云端比对，不一致直接报"主密码错误"

const items = await vault.list();
// 内部：GET /v1/items → 拿密文 → 逐条验 MAC → AES 解密

const pwd = vault.getField(items[0], 'password'); // 明文只出现在这一行

明文只存在于第三方程序的内存里，云端、日志、网络传输全程只有密文。SDK 不把密钥写磁盘，进程退出即失效。

四、完整链路（一张图看懂）

环节谁在做流通的数据是否含明文
1. 生成授权码小程序 + 云端6 位一次性码否
2. 换令牌第三方 ↔ 云端授权码 → token（云端存哈希）否
3. 拉元数据第三方 ↔ 云端kdf / iterations / salt / verifier否
4. 拉密文第三方 ↔ 云端nonce / ciphertext / mac否
5. 本地解密第三方本机主密码只在本地内存参与是（仅内存）

五、安全清单（P1 上线前必须做到）

  • 令牌只存哈希，数据库泄露无法直接使用令牌
  • 一次性授权码 5 分钟过期 + 用户二次确认，杜绝猜测与误授
  • 作用域分离：默认只读；写入需用户单独勾选，降低被篡改风险
  • 限流与审计：每令牌 60 次/分钟；记录 IP、设备名、访问条目 id，用户可见、可吊销
  • 错误信息脱敏：不暴露"该账号不存在/密码错误"等可用于探测的信息
  • SDK 不落盘密钥，避免第三方机器被入侵后长期可用
  • 文档红线声明：主密码只在调用方本地使用，任何索要主密码上传的服务都应视为危险

六、需要你拍板的 4 件事

  • ① 是否接受「只返回密文、本地解密」的安全模型（这是地基，不接受则整个方案要推翻重做）
  • ② 一期只做只读（第三方不能改你的库），可以吗？
  • ③ 浏览器插件示例现在就做，还是先只做 SDK + 命令行示例？
  • ④ 授权交互接受「6 位码 → 第三方输入 → 小程序内确认」三步吗？
