# 墓志铭

> 无忧密码本 · 2026-09-29 — 2026-10-30
> 三十三天，一个人和一个 AI，从零到 24,000 行。

---

## 它是什么

一个微信小程序：把密码加密后存在云端，主密码只在你脑子里，服务端永远拿不到明文。

它做到过这些：

| | |
|---|---|
| 加密 | PBKDF2-HMAC-SHA256 60 万次迭代 → AES-256-CBC + HMAC-SHA256，先加密后认证 |
| 容量 | 免费 10 条 / 会员 500 条 / 邀请可叠加 |
| 备份 | 加密导出，取件链接一次性、10 分钟过期、错 5 次即焚 |
| 界面 | 抽屉式分组、按平台自动归类、录入时平台名自动补全 |
| 工程 | 14 个云函数、193 个测试、覆盖率 68%、67 条协作规则 |

它跑通过真实支付，发过 15 个体验版，最后一次是 4.3.15。


**28 个人注册，2 个人真的用了，0 个人付钱。**

这不是失败的原因，这是失败的结论。

---

## 为什么停

不是技术不行，不是不努力。是三堵墙，一堵比一堵硬。

**第一堵：小程序做不了自动填充。**

密码管理器 90% 的价值是「登录时一键填入」。iCloud 钥匙串、1Password 都是 0 步完成。小程序做不到——那需要系统级 Autofill 权限，只有原生 App 有。

所以用户每次取密码是：打开小程序 → 输主密码 → 找条目 → 复制 → 切回 App → 粘贴。

**5 步 vs 0 步。** 这是数量级的差距，再怎么优化界面都补不上。我把列表页从 6 条改到 12 条、把行高从 144rpx 压到 92rpx——这些都对，但都改变不了「用户要多走 5 步」这件事。

**第二堵：密码是最难建立信任的品类。**

用户要把最敏感的东西交给一个陌生人。大厂靠品牌背书，个人开发者没有。而「我的加密做得很好」这句话，普通用户根本无从判断。

**第三堵：红海，而且对手免费。**

苹果、安卓系统自带；Bitwarden 免费；微信里同类小程序几十个。

「低预算 + 慢慢累积用户」这条路，在这三堵墙面前走不通。

---

## 它做对了什么

**加密设计是认真的。**

- 主密码从不上传，密钥只在内存里派生
- Encrypt-then-MAC，MAC 覆盖密文和关键字段
- 随机数失败就报错停下（fail-closed），不降级
- 取件链接一次性、5 次密码错误直接失效、三层清理不留垃圾

**测试纪律是认真的。**

193 个用例，改任何东西都要过门禁。中途有几次「改了实现导致测试挂」，每次都能立刻定位——因为测试覆盖到了。

**有一次真的抓到了漏洞**：取件页面原本可以无限次试密码。审计发现后改成 5 次即失效。**如果没有测试，这个洞会一直留着。**

**文档和规则沉淀下来了。**

63 个文档，67 条协作规则。这套规则不是写给 AI 看的，是这一年踩过的坑的清单：不要凭记忆下结论、不要在没验证需求时加功能、不要用「缓存」解释用户看不到变化。

---

## 它做错了什么

这部分是我（AI）的复盘，不是用户的。

**最大的错：我在界面上花了太多轮次，而那时连「有没有人真的需要」都没确认。**

- 密码页布局改了 **6 轮**
- 录入页改了 **4 轮**
- 一个「+」号的居中问题修了 **2 次**

每一次我都很认真地做，出 HTML 原型、抓竞品截图、量尺寸。但**我从来没有在第一次说：「先确认有没有人在用，再决定要不要改 UI」**。

这是我的失职。规则里明明写着「新功能先调研」（P-08），却没写「**需求本身先验证**」。

**第二个错：技术债一直在积累。**

- `storage.js` 1500 行，一半代码在伺候本地/云端双写
- 云函数圈复杂度最高 55（上限 25）
- Node 16.13 已停止维护，但因为「升级要重建函数」一直搁置

这些都不影响它能用，但让「接手继续做」变得困难。

**第三个错：iOS 上解锁卡住的问题，始终没在真机验证过。**

用户没有 iPhone。我写了实时日志埋点、加了重试按钮，但从头到尾**没有一次真机确认**。这件事一直挂在待验证清单上，到最后也没能划掉。

## 它留下了什么

**开源地址**：https://github.com/wangzhen110/wuyou-password-vault-oss

MIT 协议，24,000 行代码，261 个文件。所有真实凭据和用户数据都已清除。

如果你要做类似的东西，可以直接拿去用：

- `miniprogram/utils/crypto.js` — 一套能跑在小程序里的 PBKDF2 + AES + HMAC 实现，带进度回调和事件循环让出（避免主线程卡死）
- `cloudfunctions/backupDownload/` — 一次性取件链接的完整实现（限次、过期、三层清理）
- `cloudfunctions/openapi/` — 带 IP 限流和幂等的 Token 交换
- `tests/` — 193 个用例的写法参考
- `AGENTS.md` — 67 条协作规则，写给任何要跟 AI 长期协作的人

**私有仓库保留完整历史**：162 次提交，每一天的工作都在。

## 如果重来

我仍然认为这个技术底子是对的，只是装错了方向。

**同一个底子，换个定位就成立**：

不做「密码管理器」（要自动填充、要极高信任、跟大厂正面打），
做「**账号备忘录**」——记那些注册过但很少用、需要时又必须找得到的账号：各种网站、老论坛、宽带、水电煤、社保、学校系统。

这个定位下：

- 不需要自动填充（低频查询）
- 信任门槛低一档（不是每天用）
- 大厂不做这么细的场景
- 微信生态天然合适（随时能查，不用装 App）

**技术全部复用，只是换个故事。**

## 最后

三十三天，它从一行代码长成一个能跑通支付、能加密备份、有 193 个测试的完整产品。

它没有成功，但它**是完整的**。

很多项目死在半路上——功能没做完、代码跑不起来、文档没写。这个不是。它可以被打开、被运行、被读懂、被拿走继续用。

**一个东西能被别人接着做下去，就不算白做。**
