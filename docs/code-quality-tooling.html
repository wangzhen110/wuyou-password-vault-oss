代码质量工具调研与优化方案

面向「无忧密码本」（微信原生小程序 + 云开发云函数，10 个函数 / 28 个小程序 JS 文件 / 135 项测试）
2026-10-18

结论先说

项目已有的测试体系（135 项 node:test + 发布/备份门禁）质量高于多数小程序项目，真正缺的不是"再写测试"，而是四类基础设施： ① 静态检查（今天暴露出"部署成功但代码是空壳"这类问题，静态+部署校验能拦住）； ② 覆盖率门禁（函数覆盖仅 58%）； ③ 依赖漏洞治理（5 个 high，全在 wx-server-sdk 传递依赖里）； ④ 小程序特有的性能度量（解锁时 PBKDF2 60 万次在低端机是明显卡顿点）。

二、工具调研（按三类目标）

A. 漏洞检测

工具开源/许可能力与适配度
npm auditnpm 内置 依赖 CVE 扫描，零成本。本项目立即可用：已实测出 5 个 high，根因是 wx-server-sdk 的传递依赖。
OSV-ScannerGoogle / Apache-2.0 比 npm audit 覆盖面更广（含 GHSA、语言无关），单二进制即可跑，适合进 CI 做门禁。
Semgrepr2c / LGPL-2.1 可写自定义规则的 SAST，对本项目价值最高：可自定义"云函数必须校验 getWXContext().OPENID""禁止 console 打印 password/token""回调必须幂等（查重 entitlement_delivered_at）"等规则，把安全约定变成可执行检查。
Gitleaks / TruffleHogMIT / AGPL-3.0 密钥泄露扫描。本项目刚经历过：AppKey、AppSecret 已进过对话与后台，必须确保不进 git；这类工具能防"手滑提交密钥"。
CodeQLGitHub（受限许可） 深度数据流分析，强但重（需 CI 编译数据库），对纯 JS 小程序性价比一般，不建议现阶段引入。

B. 排查问题（静态检查 / 类型 / 结构）

工具开源/许可能力与适配度
ESLint + PrettierMIT 基础静态检查。小程序需补全局声明（wx/Page/Component/App/getApp/getCurrentPages）。能直接抓到"绑定了不存在的方法""未定义变量"这类线上一打开就白屏的问题。
TypeScript checkJs
低成本高收益		Apache-2.0 不改造代码，用 // @ts-check + JSDoc 就能校验；配合 miniprogram-api-typings 获得 wx API 参数类型提示（把"传错参数"从运行时错误变成编辑器报错）。
miniprogram-ci微信官方 npm 包 官方 CI 能力：预览/上传/包体积与依赖分析脚本化。可替代现在依赖 wechatide CLI 的人工步骤，让发版完全可重复。
c8ISC Node 原生测试的覆盖率工具，与现有 node:test 零摩擦。实测语句 78%、函数仅 58%，可直接设门禁。
madge / dependency-cruiserMIT 循环依赖与架构规则检查。本项目 utils/ 与 pages/ 已有清晰分层，可用来锁死"页面不得直接 require crypto 底层"这类边界。
jscpdMIT 重复代码检测。云函数间存在大量同构逻辑（pay/payCallback/vpay/vpayCallback 的订单与权益代码），可用它量化重复度并驱动抽公共模块。

C. 性能

工具开源/许可能力与适配度
开发者工具「体验评分 / 性能面板」官方内置 最贴近真实：启动耗时、渲染、setData 体积、内存。建议纳入每次发版的人工检查项（可截图留档）。
wx.getPerformance官方 API 自定义打点：可埋"解锁耗时（含 KDF）""同步往返耗时"，在真机上量化而不是猜。
clinic.js / 0xMIT Node 火焰图，可定位云函数 CPU 热点（如同步大包、加解密循环）。本项目的 sync 与 vpay 是最值得看的两个。
云开发监控平台内置 函数耗时 P99、错误率、调用量。可对"错误率 > 1%""P99 > 3s"设告警，比用户投诉早发现。
代码依赖分析官方内置 包体积构成。当前 606KB（主包上限 2MB），有空间但需盯着 crypto-js 等大依赖。

三、针对本项目的建议（含优先级与实施方式）

P0-1 部署后校验（今天事故的直接解药）

背景：vpay 用 CLI 部署返回 success，但函数里仍是默认 Hello World 骨架（CodeSize 286），直到真机支付才暴露。

做法：扩展现有 scripts/deploy-function.ps1，部署后自动调一次函数并断言返回结构；或直接查 CodeSize/CodeInfo 是否包含特征字符串。

# 部署后最小校验（示例思路）
1) invoke 一次（带已知入参）→ 断言返回 JSON 含预期字段
2) 或 getFunctionDetail → CodeSize 与本地 zip 大小偏差 < 20%
3) 校验失败 → 脚本非 0 退出，阻断后续发版
P0-2 ESLint + Prettier 接入（半天）

目标：把"未定义方法/变量""绑定了不存在的事件处理函数"这类会导致页面白屏的错误拦在提交前。

# 安装
npm i -D eslint prettier eslint-config-prettier

# .eslintrc.cjs 关键配置
module.exports = {
  env: { es2022: true, node: true },
  globals: { wx: 'readonly', App: 'readonly', Page: 'readonly',
             Component: 'readonly', Behavior: 'readonly',
             getApp: 'readonly', getCurrentPages: 'readonly' },
  rules: {
    'no-undef': 'error',
    'no-unused-vars': ['warn', { args: 'none' }],
    complexity: ['warn', 15],
    'no-console': ['warn', { allow: ['error', 'warn'] }],
  },
};

# 接入现有门禁：package.json
"lint": "eslint miniprogram cloudfunctions --max-warnings 40",
"test:gate": "npm run lint && npm test"

建议第一轮只报错不阻断（--max-warnings 设宽），2 周内逐步收紧，避免一次性几百条告警劝退。

P0-3 依赖漏洞治理（1 小时评估 + 半天验证）

实测 5 个 high，全部来自 wx-server-sdk 4.0.2 的传递依赖：axios（CSRF）、lodash.set（原型污染）。

做法：先在一个非关键函数（如 login）上升级 wx-server-sdk 到最新 4.x，跑该函数的测试与一次真实调用；通过后批量升级 10 个函数。 若最新版仍带漏洞，用 overrides 强制提升 axios/lodash.set 版本，并回归 payCallback 这类敏感链路。

npm audit --production          # 基线
npm i wx-server-sdk@latest      # 单函数试点
npm audit --production          # 复核归零

2026-10-18 实测结论：npm i wx-server-sdk@latest 结果是 仍是 4.0.2（已是最新），5 个 high 全部来自上游传递依赖且上游无新版，常规升级无法消除。

可行策略：① 保持版本锁定（发布清单要求 pinned），每季度复查 npm audit；② 若必须清零，用 overrides 强制 axios@^1.7，并在 login 等非关键函数上先验证云函数是否仍正常；③ 风险评估：axios 的 CSRF 漏洞主要影响浏览器环境，云函数为服务端调用；lodash.set 原型污染需攻击者控制键路径，当前调用链中无可控入口。综合判定为可接受风险、持续监控，不为此冒险改动云函数依赖树。

P1-1 覆盖率门禁 + 补关键路径（1 天）

函数覆盖 58% 意味着近一半函数从未被任何测试执行。建议门禁设为不低于当前值并逐步提升，重点补：

  • utils/crypto.js：KDF 参数校验、MAC 校验失败、旧格式兼容分支
  • utils/sync.js + cloudfunctions/sync：队列重放、冲突合并、元数据轮换
  • vpay/payCallback：重复发货、跨订单串号、金额篡改（部分已有）
npm i -D c8
"test:coverage": "c8 --check-coverage --lines 78 --functions 58 --branches 71 node --test"

先把"当前水位"锁住防倒退，再按周提升 3~5 个百分点。

P1-2 Semgrep 自定义安全规则（半天）

把项目里已经遵守的安全约定变成自动检查，防未来改坏：

rules:
  - id: cloudfn-must-check-openid
    languages: [javascript]
    message: 云函数入口必须校验 OPENID（避免越权读写）
    severity: ERROR
    patterns:
      - pattern-inside: |
          exports.main = async (event) => { ... }
      - pattern-not: |
          ... cloud.getWXContext() ...
  - id: no-secret-in-log
    languages: [javascript]
    message: 禁止把 password/token/session_key 打进日志
    severity: ERROR
    pattern-regex: console\.[a-z]+\(.*(password|session_key|paySig|AppKey)

配合 Gitleaks 做提交前扫描（gitleaks protect --staged），防止 AppKey/AppSecret 这类密钥进仓库。

P1-3 解锁性能优化（0.5 天，用户体验最直接）

实测 PBKDF2 60 万次在桌面 118ms；低端安卓估算 0.6~1.8 秒。当前是同步派生，用户感知为"点了解锁卡一下"。

  • 解锁按钮立即进入"验证中…"并显示进度文案，避免误以为卡死；
  • 同一次解锁内复用已派生的 keys，杜绝重复派生（重复 KDF 是最常见的性能浪费）；
  • 用 wx.getPerformance() 在真机打点，把"解锁耗时"变成可观测指标（记录到本地诊断页）；
  • 不要为了快而降低迭代次数——60 万次是安全基线，优化方向是体验与复用，不是削弱 KDF。
P2-1 云函数可观测性（上线后）
  • 云开发监控设告警：错误率 > 1%、P99 > 3s、调用量突增；
  • 对 sync/vpay 用 clinic.js 出一份火焰图，确认 CPU 热点（加密循环、大对象序列化）；
  • 日志规范：结构化字段（fn/action/openidHash/elapsed），禁止明文敏感值。
P2-2 架构治理（上线稳定后）
  • jscpd：量化 4 个支付/邀请云函数的重复度，抽出 common/entitlement.js（收益：改规则只改一处，这类改动今年已发生 3 次）；
  • dependency-cruiser：锁死分层规则（pages 不得直接 require crypto 底层、cloudfunctions 不得互相 require）；
  • miniprogram-ci：把预览/上传/包体积检查脚本化，替换人工点工具，发版可复现。

五、不建议现在做的事（避免过度工程）

  • CodeQL / SonarQube 全量接入：搭建成本高，纯 JS 小程序收益有限，P0/P1 做完再评估；
  • 改造为 TypeScript：迁移成本远大于收益，用 checkJs + JSDoc 拿到 80% 的类型收益即可；
  • 为覆盖率而测覆盖率：优先补 crypto / sync / 支付三条高风险路径，页面样式层不必强求。
