## 4.3.0 架构方向（已定，未排期）：云优先 + 会话内存（2026-10-23 用户拍板）

> **排期（2026-10-24 用户指示）**：该方案**往后面排**，当前不启动。优先保障 4.3.1 提审发布与日常问题修复；本方案仅作方向记录，不在近期计划内。

> **状态：方向已定、作为将来调整方向记录，未开始实施。** 触发时机：4.2.x 提审发布稳定后启动专项。

### 动机（2026-10-23 一天实测）

"本地优先 + 云同步"双写架构是当日全部架构性问题之源：端侧旧残留与云端清库后新状态打架（设置失败）、同步队列/冲突处理/pending 机制的复杂度（storage.js 1500 行中过半伺候双写）。云优先可让这类问题从架构上消失。

### 目标架构

- **数据权威在云端（密文）**；端侧**不持久化**任何密码数据（本地无密文残留）
- 解锁后：下载密文 → 主密码解密到**内存** → 会话内使用；**锁定/退出即丢弃**
- 断网：未解锁不可用（需拉数据校验主密码）；**已解锁会话内可用**（数据在内存）
- **红线不动**：端到端加密，云端永远只见密文，主密码/密钥不上云

### 收益

1. 端侧残留不一致问题根除（清库重置即刻生效，无需自动清理机制）
2. storage 层大简化（本地存储/同步队列/冲突处理全部退役）
3. 多设备天然一致
4. 本地无密文（设备被拿到时无密码数据可提取）

### 代价（已向用户披露）

1. 每次打开有 1-3 秒加载（下载+解密，随数据量增长）
2. 未解锁时断网完全不可用
3. 云开发调用量上升
4. storage.js 1500 行大重构（4.3.0 专项工作量主体）

### 已保留的实现资产（4.2.x 沉淀，重构时复用）

- 加密方案不变：PBKDF2 60 万次 + AES-256-CBC + HMAC（vault_meta 双份机制可简化为云端单份）
- **备份密码=主密码**产品决策（4.2.41）：导出免输密码、取件链接、下载页主密码校验
- backupDownload 云函数 + /bk 路由 + backup_links 集合（取件流程与存储架构无关，整体保留）

## 4.0.12 修复改密码后同步卡死（用户实报）

- **根因链**：改密码 → 记录重加密上传成功（旧 upload 正常）→ 收尾 `set_vault_meta` 因首写语义返回云端旧值 → `sameMeta` 失败 → `ROTATION_REMOTE_PENDING` 永久保留 → 之后每次同步报"云端与本地加密参数不一致"。`_doSync` 队列空早退使收尾在手动同步里也永不执行。
- **云端**：`rotateVaultMeta` CAS 实现（`old_vault_meta` 精确匹配 + `_openid` 所有权；更新 salt/verifier/iterations 三字段，kdf/version 不变）。旧测试"拒绝仅元数据轮换"重写为"仅匹配 old 才允许轮换 + 密文原样保留"——安全权衡：openid + old 精确匹配 + 客户端先重加密协议；最坏情况（用户只换 meta 不换密文）是自锁且密文仍在，可恢复。
- **前端**：`rotateRemoteVaultMeta`；finalize 两段式（set 首写 → mismatch 时 rotate）；`syncFromCloud` 轮换窗口期兜底 finalize。
- **验证**：新增云端 rotate 3 用例、storage 自愈回归 2 用例（含"队列已空收尾窗口"精确复刻用户故障状态）。

## 4.0.6 主密码轮换与设置/支付完善

- **主密码轮换**：`storage.changeMasterPassword` 按收敛协议实现——先重加密并上传全部记录（每条封套自带 salt，云端校验只看封套格式），全部上传确认后再换云端 `vault_meta`；本地提交采用日志式两阶段（journal 含新旧完整快照），中断后由 `recoverInterruptedRotation` 依据当前记录比对结果前滚或回滚，任意时刻本地都是一致状态。旧密码错误、新密码过短/相同、记录损坏、锁定会话均整体中止不做部分提交。测试 9 项（`tests/master-password-rotation.test.js`）。
- **协议边界（多设备）**：轮换窗口期内其他设备用旧密码下载到新密文记录会解密失败（记录级 MAC 失败），单设备用户不受影响；`syncFromCloud` 在轮换待收尾时先补上传再查元数据，避免手动同步被元数据比对卡死。

## 当前源码事实

- 新密码记录使用 `crypto_version: 1` 封套。源码配置 PBKDF2-HMAC-SHA256，600,000 次迭代、16 字节随机盐，派生 64 字节并拆分为 AES 与 MAC 密钥；记录正文使用 AES-256-CBC，另以 HMAC-SHA256 认证封套元数据和密文，并在解密前验证 MAC。安全随机源不可用时失败关闭。以上为源码描述，不是独立密码学审计结论。
- 旧格式主密码校验仅用于兼容：SHA-256 初始计算后再迭代 500 次；这不是新格式的 KDF，也不能称为“当前 500 轮 PBKDF2”。
- 密码记录正文以封套形式本地保存并同步。同步云函数当前只对 `passwords` 做通用上传/下载，`vault_meta` 独立处理；`categories`、`settings` 不在当前客户端队列/合并路径内，也被云函数拒绝为有效集合。同步云函数限制新上传字段为封套，并拒绝明文敏感字段；这不能证明旧云记录或备份已经迁移、擦除或不可恢复。

## 四、工程铁律（血泪教训，违者返工）

1. **CLI 部署云函数前必须 `npm install --production`**——CLI 不会装依赖，IDE 上传才会
2. 云函数首次部署报 "Creating/Updating state" → 等 45 秒重试即可，是腾讯云 API 瞬时状态
3. `wx.redirectTo` 不能跳 tabBar 页（静默失败）→ 必须用 `wx.reLaunch`
4. 交付用图片**绝不放 miniprogram/** 内（包体红线：主包目标 ≤300KB，现状 170.5KB）
5. 生物识别依赖 `setMasterKeyCache`：两处解锁成功路径都必须写缓存；设置页关开关要清 `pwd_master_key_cache`
6. automator 自动化：`cli auto --auto-port 9420`（后台，别用 head 截断防 SIGPIPE）→ `automator.connect` → `evaluate(() => wx.cloud.callFunction(...))`；`callWxMethod` 不支持嵌套路径
7. 备案「服务内容」选朴素「其他」最稳；「其他附件」入口非强制红标极易漏传，提交前逐页翻红点
8. 纯 CSS 图标依赖伪元素 → **V4 维持 WebView，不上 Skyline**
9. UI 重构纪律：逻辑零改动、一页一验、发现逻辑 bug 只记录不顺手修
10. 全程文案避开"支付/付款"字样（银行卡是备忘录性质，防审核误判类目）
